## 2. Two-Branch Sales Reporting Hierarchy

```text
SUPER_ADMIN (test.superadmin)
└── HEAD_OF_SALES (test.headofsales)
    ├── RSM_1 (test.rsm1) [North Region - REG-NORTH]
    │   └── SSM_1 (test.ssm1) [North Region - REG-NORTH]
    │       ├── ASM_1 (test.asm1) [North Corporate Sales]
    │       │   ├── BDO_1 (test.bdo1)
    │       │   └── BDO_2 (test.bdo2)
    │       └── ASM_2 (test.asm2) [North Corporate Sales]
    │           ├── BDO_3 (test.bdo3)
    │           └── BDO_4 (test.bdo4)
    └── RSM_2 (test.rsm2) [South Region - REG-SOUTH]
        └── SSM_2 (test.ssm2) [South Region - REG-SOUTH]
            └── ASM_3 (test.asm3) [South Commercial Sales]
                ├── BDO_5 (test.bdo5)
                └── BDO_6 (test.bdo6)
```

### Hierarchy Constraints & Invariants
1. **Mandatory Canonical Reporting Sequence:**
   - `BDO` $\rightarrow$ `ASM`
   - `ASM` $\rightarrow$ `SSM`
   - `SSM` $\rightarrow$ `RSM`
   - `RSM` $\rightarrow$ `HEAD_OF_SALES`
   - `HEAD_OF_SALES` $\rightarrow$ `SUPER_ADMIN`
   - `SUPER_ADMIN` $\rightarrow$ Top of hierarchy (`manager_id = NULL`)
2. **Anti-Cycle Enforcement:** Validated by trigger `trigger_validate_sales_reporting`. Cyclic or self-reporting assignments are rejected immediately.
3. **Cross-Branch Data Isolation:**
   - `BDO` can access only their own assigned records.
   - `ASM` can access only records owned by themselves and their direct subordinate BDOs.
   - `RSM` can access only records within their regional subtree.
   - `HEAD_OF_SALES` and `SUPER_ADMIN` have company-wide reporting scope.

## 3. How to Obtain Credentials & Perform Manual Login Checks

### Credential Storage Location
All passwords generated by the provisioning tool are stored locally in:
```text
C:\Users\izhar\Desktop\crm-v3\.test-credentials.local.json
```
*(This file is strictly excluded from Git via `.gitignore` and protected on disk.)*

### Manual Login Procedure
1. Verify the local development server is running:
   ```powershell
   npm run dev --workspace=apps/web
   ```
2. Open your web browser to:
   ```text
   http://localhost:3000/login
   ```
3. Enter the target work email (e.g. `test.superadmin@finlonexa.test` or `test.bdo1@finlonexa.test`).
4. Retrieve the corresponding password from `.test-credentials.local.json`.
5. Click **Sign In**.
6. Verify:
   - Application shell renders with correct employee name in header.
   - Role badge displays the assigned canonical role.
   - Navigation sidebar dynamically reflects the user's effective permissions.
   - For `BDO`, verify `sales_performance` and administration links are hidden.

## 4. Re-provisioning & Credential Rotation

To safely re-run provisioning or verify test accounts idempotently:
```powershell
npm run provision:test-accounts
```

To run the automated integration & RLS test suite:
```powershell
npm run test:integration
```

To rotate all test credentials:
1. Delete or rename `.test-credentials.local.json`.
2. Re-run `npm run provision:test-accounts`. The provisioner will generate fresh secure passwords and update auth identities.

## 5. How to Safely Disable or Deactivate Test Accounts

To deactivate a test employee without deleting their historical sales attribution:
```sql
-- Via Supabase SQL Editor or migration query:
UPDATE public.user_profiles
SET is_active = false
WHERE email = 'test.bdo1@finlonexa.test';
```
When `is_active` is set to `false`, the database RLS helper `public.is_active_employee()` immediately rejects all read/write queries from this session with 0 rows returned, and server actions reject the request.
